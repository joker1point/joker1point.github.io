portwatch · 本机端口占用归因与历史留档

把「端口被哪个进程占了」从 netstat 的一行 IP:PORT，变成可追溯的归因链路（端口 → PID → 进程名 → exe → 启动命令行 → 工作目录 → 启动时间），并把每次占用的出现 / 消失留档成可回溯的历史。

PythonpsutilFastAPI + SSESQLite WALReact 19 + Vite + TSasyncio
核心亮点
  • 性能陷阱定位：Windows 上 psutil.Process.ppid() 每次调用都会重建一次全量进程快照（约 45ms），逐进程取父进程让整轮采集从毫秒级恶化到 4476ms、吃穿 2 秒轮询周期 → 改为一次快照 + 查表后降到 73ms（保留兜底分支，因用到私有 API）。
  • 分层纪律 + 故障隔离：事件表只由采集层的真实观测追加，心跳刷新 / 对账闭合只允许改区间表；历史层投递同步非阻塞、sqlite3 全部走 asyncio.to_thread，任何 DB 异常都不影响实时 SSE 主链路。
  • 心跳缺陷的定位与修复：稳定占用不产生 delta → last_seen_at 永远等于 first_seen_at → 进程被强杀后对账闭合时取到重启时刻，占用时长被虚增（停机多久就虚增多久）；修复后长驻占用 3.4 小时内 last_seen_at 持续推进。
  • 诚实的时间语义：2 秒采样只能把变化定位在 (上一轮, 本轮] 内，字段名刻意用 first_seen_at / occurred_at，并在文档中显式声明采样不确定性。
  • 测试与 CI：16 个 pytest 用例钉住三层契约（快照结构与自端口归因 / diff 语义与保守保护判定 / 历史层三条设计纪律），GitHub Actions 四矩阵（ubuntu + windows × py3.11 / 3.13）回归。

flowwatch · 本机流量实时监控与进程归因

回答任务管理器回答不了的问题：哪个进程在跟谁通信、用了多少带宽、从什么时候开始的 —— 并把「说不清是谁的流量」如实分账（本机归因 / 属主受限 / 未归因 / 别人的流量 / 非 TCP-UDP），不混进总数里假装准确。

Pythonctypes + NpcapFastAPI + SSESQLite WALReact 19 + Vite + TSDNS / TLS SNIETW
核心亮点
  • 未归因率 36.8% → 29.8%（最小窗口 1.1%）：先给查表函数插桩拿未命中原因分布，再用 100ms 高频轮询做判别实验，把缺口拆成「短命 socket 漏拍 20.5% / 表里从未出现 79.5%」，再针对性修（promisc=0 + 本机地址白名单 + 端点/四元组两层记忆 + 自适应刷新）。
  • 两条路先被实测否掉才转向 ETW：表解析优化只有 1.6×（10Hz 要吃单核 36%）不值得；端口级推断在 CDN 场景会混。ETW 事件 ID 查官方清单才发现记忆里的 10/11 是错的（实际 12/28）。
  • 系统层三条纪律：结构体不手算偏移（ctypes 按文档顺序定义 + 导入断言尺寸 48/120/80/112）、fail-closed（本机地址校验连续失败就停用，绝不误归因）、拿不到权限就降级（非提权 state=denied，主链路照常）。
  • 历史层：连续量按时间桶聚合（每分钟每进程一行 + 域名桶 + 事件三关：出现要够格 / 尖峰要有基线 / 冷启动静默）；一次自锁事故换来「写库独立线程 + 有界队列、读接口走线程池」的故障隔离。
  • 隐私与口径都写进设计：promisc=0、不落包体、只统计元数据、只监听 127.0.0.1；域名只读明文元数据（DNS 应答 + TLS SNI）；未归因率同时给本窗口与近 60 窗滚动两个口径并附样本量。
